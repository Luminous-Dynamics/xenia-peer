# Xenia Crypto Provider Regression v1 — C1

Status: executable provider-boundary regression contract.

This tranche adds the first adversarial executable evidence downstream of the exact provider identity and dated external-evidence roots.

## Subject

The subject is the current Xenia initiator boundary:

```text
receive_kem_public_key
        ↓
1184-byte length admission
        ↓
untrusted pending bytes
        ↓
encapsulate_for_peer
        ↓
RustCrypto ML-KEM TryKeyInit
        ↓
only on success: encapsulation + session install
```

The critical distinction is:

```text
wire-length admission != cryptographic public-key validity
```

## Positive control

A fresh ML-KEM-768 key generated by a Xenia responder must:

1. have the expected 1184-byte public-key length;
2. be admitted as pending material without installing a session;
3. pass provider parsing/encapsulation;
4. produce an expected-length ciphertext;
5. install initiator session state.

This proves that the test does not merely reject every key.

## Adversarial case

The negative subject is exactly 1184 bytes of `0xff`.

Interpreted as ML-KEM's packed 12-bit polynomial coefficients, `0xff,0xff,0xff` yields coefficients `0xfff = 4095`, outside the valid field range for q=3329. The byte string therefore has the correct wire length but is a non-canonical ML-KEM encapsulation key.

Required behavior:

1. length admission succeeds;
2. no session exists;
3. `encapsulate_for_peer` reaches provider parsing and rejects with `InvalidKemPublicKey { got: 1184 }`;
4. no session exists after rejection;
5. the rejected pending bytes have been consumed and cannot be silently retried.

## Why this matters

The upstream ML-KEM line has had explicit work around encapsulation-key validation. This regression asks only what the exact Xenia-locked provider does at Xenia's actual boundary. It does not infer behavior from a later changelog or from package version ordering.

## Claim ceiling

A C1 PASS proves only that the exact tested Xenia boundary accepts a provider-generated ML-KEM key and rejects the specified full-length non-canonical key without installing session state on that exact build subject.

It does not establish complete FIPS 203 validation, IND-CCA security, constant-time behavior, memory erasure, protocol security, or correctness of untested provider paths.
