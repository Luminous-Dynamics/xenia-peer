# Xenia Ledger Verification Boundary

`xenia-ledger` is the evidence backbone for M1 consent/session events. Its job
is deliberately narrow: make a supplied sequence of consent records
cryptographically tamper-evident under an operator public key.

This document states the claim boundary so README, compliance, and sales text do
not overstate what the ledger proves.

## What verification proves

Given a list of `LedgerEntry` values and the expected operator `VerifyingKey`,
`Verifier::verify_chain` proves:

- every sequence number is contiguous and starts at zero;
- the genesis entry has a zero previous hash;
- each later entry links to the previous entry hash;
- every entry hash matches the serialized entry fields it covers;
- every entry signature verifies under the supplied operator public key.

If any prior entry is rewritten, deleted, reordered, or spliced without the
operator signing key, verification fails.

## What verification does not prove

Ledger verification alone does **not** prove:

- the operator private key was protected from theft or misuse;
- the wall-clock timestamp is externally trusted;
- the UI honestly presented the same scope the ledger recorded;
- the local OS, capture backend, browser, or daemon was uncompromised;
- a consent request was legally sufficient for a particular jurisdiction;
- a signed replacement chain was not generated by someone who controls the
  operator key.

Those are deployment, key-management, policy, and UX controls. The ledger can
record their evidence, but it cannot create those guarantees by itself.

## Required companion controls

Before design-partner or production wording, pair the ledger with:

1. restricted operator key storage and rotation rules;
2. an export format that carries the operator public key and chain metadata;
3. monotonic/session clocks or external timestamp anchoring for stronger time
   claims;
4. consent UI evidence that is bound to the session/request identifier;
5. revocation fail-closed tests covering frame, audio, telemetry, and input
   lanes;
6. an offline verifier binary or reproducible verifier command documented in
   release evidence.

## Safe external wording

Prefer:

> Xenia currently produces an Ed25519-signed, BLAKE3 hash-chained consent
> transcript that can be verified offline for tampering under the operator
> public key. A final PQ profile requires ML-DSA/SLH-DSA ledger signatures.

Avoid:

> Xenia proves consent happened.

That stronger claim requires the UI, identity, timestamp, key custody, and
policy controls listed above.
