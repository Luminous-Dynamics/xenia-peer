# RUSTSEC-2024-0415 / RUSTSEC-2024-0429 — gtk-rs GTK3 bindings

Status: accepted, ongoing dependency exception (not a "temporary until upgrade" one -- see
"Removal condition" below for why).

## Advisories

- `RUSTSEC-2024-0415` (unmaintained): the gtk-rs GTK3 bindings (`gtk`, `gdk`, `gio`, `glib`,
  `pango`, `cairo-rs`, `gtk-sys`, etc., all pinned at their `0.18.x` line) are no longer
  maintained -- the upstream repository is archived. No safe upgrade exists: the stated
  successor, `gtk4-rs`, is a different major API generation, not a drop-in replacement.
- `RUSTSEC-2024-0429` (unsound): `glib::VariantStrIter`'s `Iterator`/`DoubleEndedIterator`
  impls pass an immutable reference where the wrapped C function (`g_variant_get_child`)
  requires a mutable out-argument, which under some optimization levels leaves the pointer
  read by `CStr::from_ptr` uninitialized/garbage -- real undefined behavior, fixed upstream
  in `glib >= 0.20.0`. That fix is unreachable here for the same reason as the advisory
  above: `gtk 0.18.2` pins `glib = "0.18"` (a caret requirement), and no `gtk` release exists
  that allows `glib 0.20+` -- it's the same frozen GTK3 line, not an independently fixable
  issue.

## Why this is present

`tray-icon` (used by `xenia-launcher-shell`, `xenia-launcher-windows`, and
`xenia-launcher-linux` for the cross-platform system tray icon + menu) requires GTK3
specifically on Linux -- per its own README: "Linux (gtk Only)". This isn't a version pin
Xenia chose; it's the only backend `tray-icon` currently supports on Linux at all. GTK4
support in `tray-icon` would need to land upstream first.

`xenia-launcher-linux` additionally depends on `gtk`/`glib` directly (matching the version
`tray-icon`'s Linux backend already pulls) to build its native settings window -- this
doesn't introduce a new dependency, just makes an already-present transitive one direct.

## Xenia exposure note

`RUSTSEC-2024-0415` is a maintenance-status advisory, not a known vulnerability
(RUSTSEC "unmaintained" category, not an active CVE) -- the bindings still function
correctly, verified via a real native build/test/clippy pass of both
`xenia-launcher-shell` and `xenia-launcher-linux`.

`RUSTSEC-2024-0429` is real UB, taken more seriously: checked whether the affected code
path is actually reachable from anything Xenia's launcher stack calls. `VariantStrIter`
is only constructed by code that iterates a `glib::Variant` as an array of strings (GVariant
string-array marshaling, the kind of thing D-Bus/GSettings argument handling does) --
grepped the real cached source of `tray-icon`, `muda`, `libappindicator`, and
`libappindicator-sys` for any reference to `VariantStrIter`/`iter_str`/`Variant`
string-iteration and found none. None of Xenia's own launcher code touches `glib::Variant`
either. The vulnerable code path exists in the dependency graph but nothing in the actual
call graph reaches it.

## Removal condition

Unlike the quick-xml exceptions above (removable by a routine `cargo update` once upstream
crates bump their requirement), these are removable only by one of:

- `tray-icon` (or `muda`) gaining a GTK4 backend and Xenia migrating to it, or
- switching the Linux tray icon away from `tray-icon` to a different crate/approach
  entirely, or
- the gtk-rs GTK3 bindings being un-archived / a maintained fork emerging that can take the
  `glib >= 0.20.0` fix.

None of these are scheduled work. Re-evaluate if `tray-icon` publishes GTK4 support, or if
any future code (ours or a dependency's) starts actually calling into `glib::Variant`
string iteration -- at that point RUSTSEC-2024-0429's "unreachable in practice" framing
above stops holding and this needs to be revisited as a real, live risk.

Validation commands:

```bash
cargo deny check advisories bans licenses sources
cargo tree -i gtk@0.18.2
cargo tree -i glib@0.18.5
grep -rln "VariantStrIter\|iter_str" <path-to-cached-tray-icon/muda/libappindicator-sources>
```
