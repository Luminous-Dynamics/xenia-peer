## Stack-integrity and automation-authority rules

Force-rewriting a stacked base branch changes GitHub's PR base ref but does not rewrite descendants' Git commit parents. After #37 was collapsed to its clean final head, #34 became `ahead 2 / behind 1` and its PR diff silently included the superseded #37 root. #34 and #40 have now been repaired by tree-preserving delta transplantation and verified as one-commit successors. #44 overlaps a root-repaired source file and is intentionally blocked until a true three-way restack can preserve both deltas.

For security stacks, every rewritten parent requires an explicit descendant ancestry/diff audit. A PR is not considered clean merely because its configured base branch name is correct. Reviewed head/base ref names and repository identities are now bound alongside SHAs, parents, and exact changed-file sets.

For code-producing security automation, transformation/compilation/execution and repository mutation are separate authority domains. Candidate code SHOULD be transformed and qualified in a read-only job with no persisted repository credentials; only an already-qualified, hash-bound capsule may cross into a minimal write-capable materialization/publication job, and that job SHOULD NOT compile or execute the candidate. Candidate publication targets a separate collision-checked ref before any real review branch is rewritten. This pattern is now used by the #44 restack constructor, #31 causal-authority repair constructor, and #240 receiver-Ack containment constructor.
