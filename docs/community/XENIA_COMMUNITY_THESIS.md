# Xenia Community Thesis

Status: post-RC1 community note.

Xenia can have a community if it is framed honestly.

It should not be presented as a mature remote desktop replacement today. RustDesk and other tools are the practical operational choices for immediate remote access.

Xenia's community should form around a different thesis:

Remote access should be powerful without being opaque.

## What Xenia stands for

Xenia exists to explore accountable remote presence:

- no silent remote control
- no hidden operator authority
- consent as a first-class session primitive
- audit trails that matter
- secure defaults
- self-hostable infrastructure
- release evidence instead of vague trust claims
- future-ready protocol work, including PQC/WASM feasibility

## Who might care

Early community members may include:

- self-hosting users
- privacy-focused users
- security engineers
- FOSS infrastructure builders
- sysadmins and support engineers
- Rust/WASM protocol hackers
- people who care about digital sovereignty
- organizations that need remote support without silent operator power

## Honest project posture

Xenia should say:

- use RustDesk for immediate practical remote access
- use Xenia if you care about accountable, auditable, consentful remote presence
- do not trust product claims until benchmarks and end-to-end demos exist
- help build the trust layer remote access should have had from the start

## Community promise

The project should be unusually honest:

- no production claims before evidence
- no security claims without threat models
- no performance claims without benchmarks
- no hidden operator privilege
- no silent weakening of consent or audit guarantees

## First community milestones

Before broad outreach, Xenia should have:

1. A clear README.
2. A local demo that works quickly.
3. A contributor guide.
4. A security policy.
5. Good first issues.
6. A comparison page.
7. A short M1 vertical slice plan.
8. A clear statement of what is not ready.

## Decision

Xenia's community should be built around trust, consent, auditability, and disciplined engineering rather than feature parity with existing remote desktop tools.
